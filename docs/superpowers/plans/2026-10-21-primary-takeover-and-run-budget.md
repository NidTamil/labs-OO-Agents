# Primary takeover and ten-task budget implementation plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans, with focused red/green tests and independent review. Continue the existing review branch; do not launch live controls from this plan.

**Goal:** Implement the operator-approved automatic GLM-to-DeepSeek takeover and 15,000-request aggregate ceiling without resetting task custody or misattributing evidence.

**Architecture:** A controller-owned, one-way route transition keeps the existing native session, task clock and tool state. Every provider dispatch consumes a durable request reservation. DeepSeek primary requests share the 1,410 primary/memory pool; its 90 advisory requests retain the 30/40/20 role allocations. A separate signed ten-task budget binds the aggregate ceiling and eventual time/spend decisions.

**Tech stack:** Existing Python controller, SQLite, Anthropic-format streaming, pytest and uv. No new dependency.

**Spec:** Direct decisions recorded in `reviews/scored-ten-task-prep-decisions_2026-10-20.md`; this document specifies their implementation. The parent readiness ledger is `docs/superpowers/plans/2026-10-11-scored-native-campaign.md`.

## Constraints and design rulings

- Per task: 1,500 total, 1,410 shared primary/memory requests, 90 DeepSeek advisory requests. Per ten-task run: 15,000 total. Failed, cancelled and ambiguous dispatches consume reservations; no refunds.
- The operator directly approved DeepSeek using the remaining primary pool, so total DeepSeek use may exceed 90. Existing advisory token/time limits and the 43,200-second task clock remain unchanged. The four-hour limit applies only to the next reconnect control.
- Start on GLM; switch once to DeepSeek only for classified availability failure before any downstream response. No switch back, new attempt, new native home, second Send or replay after text/tool output. Keep already admitted concurrent calls bound to their original provider.
- Ruling: initially restrict transparent takeover to a pre-response failure. Midstream failures retain existing bounded interruption/halt semantics. This avoids splicing providers into one SSE message or duplicating a tool; wider recovery requires additional native evidence.
- Never switch for refusal, policy denial, authentication failure, cancellation, budget exhaustion, identity drift, credential disclosure, invalid usage, malformed arguments or audit failure.
- Ruling: use DeepSeek's documented Anthropic-compatible endpoint, `https://api.deepseek.com/anthropic`, for the primary role. This avoids inventing a Chat Completions adapter. Validate unsupported features before dispatch and keep advisory Chat Completions unchanged. Public documentation is not live certification.
- DeepSeek documents `deepseek-flash` as currently served by V4.1-Flash-1017. This remains a moving API alias, not immutable weights. Preserve returned identity/version/fingerprint separately; final signed identity acceptance remains an admission decision.
- Preserve all historical signed epochs and exact old loaders. New route/accounting/final-proof behavior requires explicit new versioned identities; no silent upgrade of old evidence.
- Aggregate elapsed time is **120 hours (432,000 seconds)**, including staging and final cleanup, and aggregate model spend is **USD 500 (500,000,000 USD micros)**, by direct operator decisions. This includes takeover, memory and failed attempts. Prepaid-plan credits require a separately verified allowance; preparation controls have separate budgets. Measured metering, signer/public trust, live certification, root reserve and signed admission remain pending. A request-only component cannot be promoted to admission-ready.

Sources checked 21 October 2026: [DeepSeek Anthropic compatibility](https://api-docs.deepseek.com/guides/anthropic_api/) and [current model mapping](https://api-docs.deepseek.com/updates). The former documents streaming, tools and message support along with ignored/unsupported fields. The latter maps the API alias to the 1017 release at the observation time.

## Review focus

1. Concurrent requests at a final allocation/run slot must not overshoot; ambiguous writes cannot release a dispatch.
2. Local request IDs, provider-attempt IDs and actual model identities must not collapse into one falsely attributed request.
3. A provider failure after response exposure cannot replay tools or cause a new Send.
4. Post-oracle memory calls must consume the same run budget before next-task advancement.
5. Old signed evidence must remain verifiable under its original schema, without accepting new evidence through old proof rules.

### Proposed file and API ownership

All Python module names below are proposed files under `examples/cybergym/nooa_cybergym/leaderboard/`.

1. **`budgeted_subset_ui_transport.py`** provides `SubsetSshUiTransport` with bounded canonical schema-two `poll`, `claim` and `ack` framing over the existing outbound authenticated SSH pattern. Frozen configuration supplies the target and allowlisted remote argv; callers cannot supply arbitrary remote paths or commands. A claim includes the signed command and durable workstation reservation nonce. The signed response binds that nonce, exact command hash, preparation binding and fence. APIs retain exact authenticated bytes, including the complete acknowledgement, rather than accepting selected status fields. The existing 16 KiB acknowledgement and 32 KiB stdout limits cannot carry the proposed 32 KiB command, 64 KiB observation and 96 KiB acknowledgement contracts. Use explicit versioned preparse bounds, including framing/envelope overhead; reject overflow without truncation and do not loosen the legacy endpoint.
2. **`budgeted_subset_ui_rpc.py`** is a POSIX forced/allowlisted SSH shim to an already-running controller-owned Unix-socket broker. The broker uses the already-acquired runtime signer; neither shim nor Windows producer obtains a private signing key or approval authority. Socket ownership, peer checks and the exact registered preparation constrain access. This is neither a new network listener nor a general signing service. The broker rechecks actual subset state, resource deadline and current fence before granting an open or Submit effect; cleanup remains possible after stop. Broker absence, restart or ambiguous response fails closed.
3. **`budgeted_subset_windows.py`** is the persistent trusted Windows producer with pinned configuration, durable ownership/observation journal and a narrow platform backend. It validates the exact preparation and independent workstation/runtime pins before consuming commands. It owns every child and helper through the process/job protocol below and retains incomplete ownership after failure. ### Ownership before effects and cleanup observations

The controller registers the exact preparation binding before publishing open. The producer records its reservation nonce and authenticated claim through local custody, then durably records the ownership intent, command hash, claim hash and preparation identity before creating any child. Every effect rechecks the current local claim/fence and applicable fresh broker permission; queued Submit commands lose permission after the fence is sealed.

The intended platform boundary is a persistent supervisor with a per-preparation Windows Job Object, breakaway disabled and kill-on-job-close behavior. Child processes, including tunnel, editor and Send helper, are created suspended and assigned to that job before resuming. Held process handles supply exact PID, creation time and executable identity; the journal also binds executable hash, argv/profile/tunnel configuration and job membership. Failure to assign or persist identity prevents Resume. Executable verification must prevent replacement between hashing and creation, for example through an appropriate held file handle. Any platform constraints that prevent this ownership sequence are blockers to implementation acceptance, not grounds to resume an unowned process.

Cleanup first seals the local fence. It uses held handles and rechecks PID, creation time, executable and recorded ownership before terminating only owned identities. A reused PID belongs to a different process: the original exit and unrelated replacement must be distinguished without terminating the replacement. Cleanup waits within a bound and performs fresh job/process enumeration before producing evidence. Unrelated preparation entries remain unchanged. Missing identity, access denial, incomplete enumeration, surviving or late children, and persistence failures preserve ownership and an incomplete or ambiguous result. No broad executable-name kill or legacy run-wide discovery may satisfy this contract.

The durable record must survive an open failure or supervisor crash without losing incomplete ownership. Kill-on-job-close is a proposed fail-closed platform mechanism, not evidence that it works in the deployed configuration. A process that could exist without a durable ownership record must remain recoverably attributable to the preparation; a journal/Job Object gap cannot be converted into successful cleanup.
